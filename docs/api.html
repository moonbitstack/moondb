pub(open) trait AsyncCursor {
  async fn next(Self) -> Row? raise DbError
  async fn close(Self) -> Unit
}

The async counterpart of Cursor — a forward-only cursor whose next is awaited. A wire driver reads the next row off the socket when it is asked for, which is an I/O round trip and therefore async; the synchronous Cursor cannot express that, so a networked backend has no way to stream through it.

The resource discipline is Cursor's: MoonBit has no finalizer, so a driver-backed cursor MUST be drained (next until None) or [closed], or the statement leaks and the connection is left mid-result. AsyncArrayCursor is the materialised fallback, for a driver with no incremental fetch.

close does not raise, mirroring Cursor::close: abandoning a cursor is best-effort. A driver whose close has to do I/O — draining an unread result off the wire — swallows the failure, because a connection whose drain failed is already unusable and the next statement on it will say so.

pub(open) so out-of-tree drivers implement it.

## Why there are two driver traits

Driver is synchronous, which fits a backend whose calls block in C: moonsqlite steps a prepared statement and returns. A backend reached over TCP cannot be written that way in MoonBit, because the only socket stack (moonbitlang/async) is async-only and an async fn cannot be called from a synchronous one. A wire driver forced to conform to Driver can therefore do nothing but raise — and, worse, it raises from ping too, so a Pool with pre_ping judges every one of its connections permanently unhealthy.

AsyncDriver is the seam for those backends. It is a peer of Driver, not a replacement: a synchronous backend keeps implementing Driver and does not become async to satisfy anything here. The two traits are deliberately identical method for method, so a query layer can offer a sync and an async path that read the same.

Everything Driver documents about the calling convention holds unchanged: sql carries positional placeholders in the backend's own spelling, params supplies one Value per placeholder in order, and values are bound out-of-band rather than interpolated.

This trait declares async methods but pulls in no async runtime — moondb stays dependency-free and still compiles on every backend. Only a driver that implements it, and a caller that runs it inside an event loop, need the runtime.

pub(open) so out-of-tree drivers (moonpostgres, moonmysql, …) implement it.

pub(open) trait Cursor {
  fn next(Self) -> Row? raise DbError
  fn close(Self) -> Unit
}

A forward-only cursor over a query's rows — the streaming counterpart to Driver::query. Where query materialises the whole result, a cursor yields one Row at a time, Python DB-API's fetchone).

next advances and returns the next row, or None once the result is exhausted; close releases the cursor early (a driver holding a server-side cursor or prepared statement frees it here). A driver with real incremental fetch — moonsqlite steps its prepared statement, an async driver reads rows off the wire on demand — returns a live cursor; the default Driver::query_stream falls back to an ArrayCursor over a materialised result, which honours the same interface without the memory bound.

A live cursor holds a resource (a prepared statement, a busy connection). MoonBit has no finalizer to reclaim it, so a driver-backed cursor MUST be fully drained (next until None) or closed — abandoning it leaks the statement or leaves the connection mid-result. The materialised ArrayCursor holds nothing and is safe to drop.

pub(open) so out-of-tree drivers implement it.

## The binding contract

execute and query both take (sql, params). sql carries **positional placeholders** and params supplies one Value per placeholder, in order. A driver is expected to bind values out-of-band rather than interpolate them into the SQL text. A driver that cannot — the MySQL text protocol has no out-of-band binding until prepared statements land — has to escape for the server's actual sql_mode, and must say so in its own documentation.

The placeholder token itself is dialect-specific and chosen by the driver (SQLite/MySQL use ?, PostgreSQL uses $1, $2, …); a query layer that emits SQL for a given backend uses that backend's token. moondb fixes the calling convention (ordered params array), not the spelling.

* execute runs a statement that returns no rows (INSERT/UPDATE/DELETE/DDL) and reports an ExecResult. * query runs a statement that returns rows and materialises every Row. * begin / commit / rollback bracket an explicit transaction. Nesting (savepoints), isolation levels, and read-only hints are driver concerns layered on top; the base contract is the three flat operations. * close releases the connection. It does not raise: closing is best-effort and idempotent.

This trait is pub(open) so out-of-tree drivers (moonsqlite, moonpostgres, moonmysql, …) can implement it.

A dependency-free, in-memory reference Driver. It exists for two reasons: to prove the interface is implementable end to end, and to give query layers built on moondb (moonorm and friends) a real test double they can run against with no database and no native backend — it compiles on every target.

It is a deliberately naive echo store, **not** a SQL engine: it does not parse sql. pub(all) struct Named {
  sql : String
  slots : Array[String]
}

A statement whose :name parameters have been rewritten to the backend's own positional spelling, together with the name of the value each position takes.

The rewrite happens once, before the statement reaches the server: PostgreSQL's extended-query protocol wants $1, $2, …, SQLite and MySQL want one ? per parameter. bind(#bind) turns a name-keyed argument map into the ordered array the driver expects, so a query layer writes SELECT * FROM hero WHERE id = :id AND realm = :realm once and runs it on all three backends.

The rewrite is a lexer, not a search-and-replace: a :name inside a string literal, a quoted identifier, a -- / # / /* */ comment or a PostgreSQL $tag$ … $tag$ body is left alone, and neither :: (a cast) nor := (a named function argument) opens a parameter.

test "named parameters become the backend's own spelling" {
let q = @moondb.rewrite_named(
"SELECT * FROM hero WHERE id = :id AND realm = :realm",
@moondb.Dialect::Postgres,
)
assert_eq(q.sql, "SELECT * FROM hero WHERE id = $1 AND realm = $2")
assert_eq(q.slots, ["id", "realm"])

let m = @moondb.rewrite_named(
"SELECT * FROM hero WHERE id = :id",
@moondb.Dialect::Mysql,
)
assert_eq(m.sql, "SELECT * FROM hero WHERE id = ?")
}

A statement that is prepared once and run many times with new values.

Driver::execute and Driver::query prepare, bind, run and discard in one call, which is right for a one-off and wasteful for a loop: a server that has already parsed and planned a statement can execute it again with nothing but the values. A Stmt is that handle. bind(#bind) replaces the values, execute(#execute) and query(#query) run the statement, and close(#close) releases the server-side resources.

A handle is not a connection: it belongs to the connection that prepared it, and running it after that connection closed raises Closed. It is not safe to share between tasks for the same reason — one wire, one statement at a time.

test "one statement, two bindings" {
let db = @moondb.MockDriver::new()
let stmt = db.prepare("INSERT INTO hero (id, name) VALUES (?, ?)")
stmt.bind([@moondb.Value::Int(1), @moondb.Value::Text("Nova")])
stmt.execute() |> ignore
stmt.bind([@moondb.Value::Int(2), @moondb.Value::Text("Iris")])
stmt.execute() |> ignore
stmt.close()
assert_eq(db.row_count(), 2)
}

pub struct Txn[T] {
  driver : T
  mut depth : Int32
}

A transaction that nests: the outermost run(#run) opens a real transaction, every nested one opens a savepoint, and an error undoes only the work of the level that raised.

Driver::begin / commit / rollback are flat, which is all a backend has to offer, but application code nests: a service method opens a transaction, calls a repository method that opens one too, and the inner failure must not discard the outer work. Txn closes the bracket around a body so the pairing cannot be forgotten, and derives the savepoint name from the nesting depth so two levels never collide.

test "a nested body that fails keeps the outer work" {
let db = @moondb.MockDriver::new()
let tx = @moondb.Txn::new(db)
tx.run(fn(tx) raise @moondb.DbError {
tx
.driver()
.execute("INSERT INTO hero VALUES (?, ?)", [
@moondb.Value::Int(1),
@moondb.Value::Text("Nova"),
])
|> ignore
// The inner level fails; only its own work is undone.
(tx.run(fn(_tx) raise @moondb.DbError {
raise @moondb.QueryError("inner failed")
}) catch {
_ => ()
})
|> ignore
})
assert_eq(db.row_count(), 1)
}

}

A fixed-ceiling connection pool over any Driver. Opening a database connection is expensive — a TCP handshake and auth round trip for a networked backend — so a server hands out a small set of connections and reuses them instead of opening one per request.

The pool is generic in the concrete driver D rather than holding &Driver trait objects, so acquire gives back the real driver type and a caller keeps access to backend-specific methods (SQLite's exec_script, a driver's prepared-statement handle). new takes a make factory that opens one fresh connection; the pool calls it only when no idle connection is available and the open count is still below max_size.

Beyond plain reuse, the pool keeps a connection healthy over its lifetime.

* **pre-ping** (pre_ping) — before an idle connection is handed back it is probed with Driver::ping; a connection that fails the probe is closed and skipped, so a caller never receives a connection the backend has already dropped. * **max lifetime** (max_lifetime_ms) — a connection older than this is retired on acquire and replaced with a fresh one, so long-lived pools recycle connections a load balancer or the server may have aged out. Age is measured with an injected clock, exactly as database/sql swaps nowFunc in tests; the default clock disables the check. * **acquire timeout** (acquire_timeout_ms) — the wait budget an exhausted acquire is allowed. See the note on synchrony below.

It is synchronous and single-threaded by design — moondb's base contract is sync, and MoonBit's pure backends have no shared-memory threads — so acquire never truly blocks: nothing else can return a connection while one call waits. A request that finds the pool exhausted therefore fails immediately rather than sleeping; acquire_timeout_ms is carried into that failure's message and is the budget a driver running on an async runtime honours when it layers real waiting on top. Use try_acquire for the non-raising "give me one only if free" path. The reuse, ceiling, health, and lifecycle bookkeeping all live here.

The counting is moonpool's Pool: live, idle and lent, each lent connection's birth recognised on its way back so max_lifetime counts from creation. So is the optional ward in front of the database: backoff after failed connects, a token bucket spacing reconnections, a breaker, a shedder. This type adds only what needs a driver — opening, closing, probing.

A connection pool for an @moondb.AsyncDriver — the counterpart of @moondb/pool.Pool for a backend reached over the network.

It exists because a synchronous pool cannot do the one thing an exhausted pool is supposed to do: wait. In @moondb/pool.Pool nothing can return a connection while a caller is inside acquire, so a full pool fails immediately and acquire_timeout_ms only reaches the error message. Here the caller is a task in an event loop: other tasks keep running while it waits, so a full pool parks the caller on a permit and wakes it when a connection comes home. The division of labour mirrors the sync pool: @moonpool keeps the accounting — live, idle, lent, each connection's birth time — and this type adds what only a driver can do (opening, probing, resetting, closing) plus the permit that makes an exhausted acquire wait.

  driver : T

A @moondb.Driver seen as an @moondb.AsyncDriver, so a backend whose work happens inside a C call can be handed to code written against the asynchronous seam — the checkpoint store of an agent framework, a retrieval index, a server that runs one event loop for every dependency.

The two traits are method-for-method identical, so the bridge is a delegation and nothing more: each async method calls its blocking twin and returns its result. There is no thread, no queue and no wake-up, because there is nothing to wait for — SQLite steps a sqlite3_stmt and returns.

What the bridge does not do is as important. The call runs on the task's own thread, so it occupies the event loop for as long as the driver takes: that is the right trade for a backend answering in microseconds out of the page cache, and the wrong one for a backend answering in milliseconds over a socket — a networked backend implements @moondb.AsyncDriver itself, where the wait is real and other tasks keep running through it. Nor does the bridge serialise: a driver that is not safe to use from two tasks at once is still not safe here, so give each task its own connection, or park them behind @moondb/apool.AsyncPool, which hands one connection to one caller at a time.

What it does keep is everything beyond the base contract: prepare hands back the driver's own server-side handle rather than a buffered re-run, query_stream keeps the driver's live cursor rather than materialising the result, and dialect and capabilities come from the wrapped driver, so a query layer sees the real backend underneath.

Run the conformance matrix against one live connection and report, case by case, which parts of the @moondb.AsyncDriver contract the backend honours.

## What it checks

The matrix is the contract's own text turned into cases: connect, bind and read back, prepare once and re-run, bracket a transaction, nest one through a savepoint, survive every @moondb.Value case the dialect has a column type for, and classify two failures the way the error model says they must be classified. It is a conformance suite, not a SQL-engine test: it says nothing about whether the backend's SQL is right, its planner fast, or its own extensions present. The byte channel a connection speaks the PostgreSQL v3 protocol over.

A real connection uses a socket — plain, or a TLS session layered on one. The protocol code above it, though, only ever needs three things: read exactly n bytes, write these bytes, close. Pulling that out of PgConn is what lets the state machine (statement sequencing, the streaming guard, error draining, COPY, notifications) be tested against a scripted peer with no machine and no server behind it: pipe(PgWire::pipe) hands it one end of an in-memory pipe pair and the test plays the server on the other.

## The async wall, and what it means here

moonbitlang/async sockets are asynchronous, but @moondb.Driver's methods are synchronous, and MoonBit forbids calling an async function from a non-async one. The bridge is @async.run_async_main, which spins an event loop, runs an async body to completion, and returns — the same hook the toolchain uses to enter async fn main.

A socket does **not** survive across two such event loops (each tears its file descriptors down; verified empirically), so every execute/query opens a fresh connection, authenticates, runs its one statement, and closes. That is correct and efficient enough for autocommit work — which is exactly what the moondb roundtrip is — but it means a transaction cannot be held open across separate Driver calls. begin/commit/rollback therefore raise a clear error directing callers to the asynchronous MysqlConn API, which owns its socket for its whole lifetime and brackets real transactions. This is a language constraint, not a shortcut, and it is documented in the README.
